# 다음 교재로 넘길 때 — 인수인계

민사소송법 교재로 만든 파이프라인을 다른 교재(특허법 등)에 이어 쓰기 위한 문서다.
**새 세션은 이 파일부터 읽으면 된다.**

프로그램은 새로 만들지 않는다. `book2md` 는 교재를 가리지 않게 만들어 두었고(§9),
교재마다 다른 것은 **교재별 설정 파일**에 있다. 설정은 층으로 쌓는다.

```
config.yaml           공통 — 사건번호 문법, 각주·두문자 판정, 검증 기준
config-민소법.yaml     교재별 — 사람이 확인한 정정, 책 제목, 그 판형의 오인식
config-patent.yaml    교재별  ← 새 교재는 이 파일 하나를 만든다
```

**`config-patent.yaml` 은 이미 만들어 두었다.** 민소법 설정에서 갈라내
사건번호 부호(심판번호 당·원·취·정)·조문 법령명·띠 낱말을 특허법에 맞춰 놓았다.

특허법 교재는 **기본서 + 사례집 두 권이고, 출판사가 민소법과 다르다.**
그래서 판형에 매인 설정은 하나도 믿을 수 없다. 두 갈래로 나눠 두었다.

- **중립화** — 민소법 판형에 맞춰 둔 것 중 **글자를 실제로 바꾸는** 규칙은
  꺼 두었다. 끈 채로 돌려도 글자는 하나도 잃지 않는다. 구조가 덜 잡힐 뿐이다.
- **`TODO(진단)`** — 실물을 봐야 정해지는 자리. 민소법 값이 그대로 남아 있다.

```bat
convert --book patent diagnose "특허법 PDF 폴더" --out 특허출력
convert --config config.yaml --config config-patent.yaml diagnose …   :: 같은 뜻
```

`--book <이름>` 은 `config-<이름>.yaml` 을 공통 설정 위에 얹는다.

> **아직 고를 것이 남았다.** `config-patent.yaml` 은 지금 공통 설정을 통째로
> 베낀 634줄짜리다. 그 상태로도 돌지만, 공통 규칙을 고쳐도 특허법에는 안
> 닿는다. 특허법에만 해당하는 40줄 남짓(심판번호 부호·법령명·띠 낱말·
> `TODO(진단)`)만 남기고 나머지를 지우면 층이 제 노릇을 한다.

**복사본을 만들지 말 것.** 공통 규칙을 고치면 두 교재에 함께 반영돼야 한다.
이번에 고친 결함 다섯(띠 낱말, 목차 항목 재사용, 러닝 헤더, 점검기 오탐 셋)은
전부 스캔+OCR 교재의 일반 결함이라 특허법에서도 똑같이 난다.

교재별 파일에는 **교재를 넘어가면 해를 끼치는 것만** 둔다. 민소법 원문에서
사람이 확인한 정정 14개가 특허법 원문에 적용되면 안 된다.

## 전체 파이프라인

```
[1] PDF → 마크다운          convert diagnose → convert all
[2] 절 제목 점검 → 고치기    convert audit-sections → config 손질 → 재변환
[3] 기본서 ↔ 사례집 매핑     mapping build → review → confirm
[4] 노트 생성               Claude 가 SKILL.md 를 읽고 md → md
```

[4]는 코드가 아니다. 스킬 문서를 읽은 Claude 가 하는 일이다. 이 리포는 [1]~[3]까지다.

## 명령

| 명령 | 하는 일 |
|---|---|
| `convert --book <교재> …` | 교재별 설정을 함께 읽는다. **빠뜨리면 정정이 조용히 빠진다** |
| `convert diagnose <PDF폴더>` | 사전 진단. **이걸 건너뛰면 run 이 막힌다** |
| `convert all <PDF폴더> --out <출력>` | 진단→변환→검증→교차검증 한 번에 |
| `convert audit-sections <출력> --out audit.md` | 절 제목 전수 점검. 재변환 없이 변환물만 읽는다 |
| `convert probe <PDF> --lines --pages 170-173` | 줄마다 무엇으로 읽혔는지. 헤딩이 안 잡힐 때 |
| `convert apply-decisions <결정표>` | 두문자 결정표에 표시한 대로 config 를 고친다 |
| `convert mapping build <출력> -o mapping.yaml --report dbg.md` | 기본서↔사례집 매핑 |
| `convert mapping review / confirm / validate` | 승인 대기 목록 · 승인 · 검증 |

두 도구 다 **아무것도 자동 승인하지 않는다.** 사람 판단이 필요한 자리(두문자 결정,
매핑 승인, 사건번호 육안 검수)는 리포트로 넘긴다.

## 교재가 바뀌면 손대는 곳

설정(특허법은 `config-patent.yaml`)에서 이 항목들만 보면 된다.

| 항목 | 무엇 |
|---|---|
| `preserve.case_suffixes` / `known_suffixes` | 사건번호 부호. 특허는 `후`(대법원)·`허`(특허법원)가 이미 들어 있다 |
| `preserve.year_min` / `year_max` | 4자리 연도 범위 |
| `legend.outline.keywords` | 논점 윤곽 띠에 나오는 낱말. **교재마다 다르다** |
| `legend.sidenote.pattern` | 옆번호 모양 (`sE-8` 꼴) |
| `running.never_heading` | 책 제목. 머리말이 절 제목이 되는 것을 막는다 |
| `profiles.<이름>.headings` | 절 번호 모양 (`I.` `1.` `제N절`) |
| `profiles.<이름>.label` | 프론트매터 `source:` 에 적히는 이름. 매핑이 이걸로 기본서/사례집을 가른다 |
| `normalize.roman_heads` | 로마자 번호 오인식 표 (`I` ← `l` `|` `।` `仁j`) |
| `normalize.corrections` | **사람이 확인한 정정만.** 프로그램은 스스로 고치지 않는다 |

절대 건드리지 않는 것: §4.8 금지사항 — 맞춤법 자동 교정, 문장 재구성·요약,
판시 문언 수정, 한자를 한글로 변환. 정정은 `corrections:` 로만 한다.

## 이번에 겪은 함정 — 다음 책에서도 똑같이 겪는다

### 목차 띠가 모든 것의 근거다

논점 첫 줄의 `◎ 의의-내용-예외-효과` 띠는 **뭉개진 절 제목 복구·검증·절 점검
셋 모두의 근거**다. 띠 하나를 못 읽으면 그 논점의 절이 줄줄이 묻힌다.

`convert audit-sections` 의 맨 윗줄 `목차 띠를 읽은 파일 N/M개` 를 **가장 먼저**
본다. 낮으면 다른 숫자는 볼 필요가 없다.

실측: 띠 9개를 못 읽은 이유가 `keywords` 목록이었다. `◎ 개시–진행–종결–재개`
가 넷 다 목록에 없어서 띠가 아니라고 판정했다. 지금은 표지(`◎ & ※`)가 있고
토막이 셋 이상이면 낱말을 요구하지 않는다. 표지가 없는 교재라면 `keywords` 를
그 교재의 말로 새로 채워야 한다.

### 반복 횟수로 머리말을 판정하지 말 것

`I. 의의 및 취지` 는 논점이 135개면 77곳에 나온다. 반복은 정상 절의 성질이다.
러닝 헤더는 **책 제목 문자열**로 가른다 (`running.never_heading`).

### 목차 항목 하나를 여러 절이 나눠 쓰는 것은 정상

`요건-당사자 동일`, `요건-소송물 동일`, `요건-권리보호이익` 셋이 띠의 `요건`
하나에 대응한다. 번호가 성한 절끼리는 서로 막지 않는다. 번호가 뭉개진 줄이
뒤늦게 같은 항목을 집을 때만 가짜다.

### 띠와 절은 이름이 다르다

띠는 축약형, 절은 완전형이다 — `협의소송자료` ↔ `III. 협의의 소송자료 준별과 완화`.
완전 일치로 대조하면 진짜 절이 「짝 없음」으로 나온다.

### 매핑은 답안 목차가 주력이다

지침이 정한 세 근거(제목 키워드·사건번호·두문자)만으로는 실물에서 판정이 안 선다.
사례집은 판시를 요지로만 압축해 실어 사건번호가 문제 323개 중 294개가 0건이었다.

대신 **사례집 답안 목차가 기본서 절 구조를 그대로 옮겨 적는다.**
`E-2 > 3. 일부청구 후 잔부청구 중복소제기 해당 여부` ↔ `III. 중복소제기`.
이것만으로 사람이 손으로 확인한 정답지 8건이 배점까지 그대로 재현됐다.

- 답안 목차 대조는 **장이 맞은 안에서만** 한다. 안 그러면 절 500 × 문제 300 이
  이름만 겹쳐 다 이어진다 (실측 12,177쌍).
- `의의`·`내용`·`요건`·`효과` 같은 짧은 절 이름은 어느 장에나 있어 뺀다.
- 총점은 제목이 아니라 **문제 지문 끝**에 있다 — `…설명하시오. (14점)`.
- `role` 의 25% 문턱 분모는 총점이 아니라 **읽은 배점의 합**이다. 총점을 쓰면
  배점을 덜 읽었을 때 role 이 사안 적합도가 아니라 OCR 성공률을 재게 된다.
- 사례집 앞머리 **목차 쪽**을 문제로 읽지 않는다. 같은 번호가 두 번 실리면
  진짜 문제의 사건번호·두문자가 빈 껍데기에 가려진다.

### 색상 추출은 껐다

스캔본은 OCR 글자가 전부 검정이라 색이 그림 픽셀에만 남는다. 한 번 켜 봤으나
본문 강조는 **굵은 검정**이고 청색은 제목·두문자뿐이어서, 임계값을 낮추면 가짜
강조가 만들어졌다. 지금은 `preserve.color.bold_from_image: false`. 강조 범위는
노트 단계에서 AI 가 직접 판단한다 (`OUTPUT.md` §5 참조).

### 일하는 순서

한 번에 전 범위를 돌리지 않는다. **하나 먼저 → 검증 → 규칙 보완 → 전체.**
그리고 **고치기 전에 세기부터** 한다. 표본 몇 줄로 진단해 고치면 그 몇 줄에만
맞춘 수선이 된다. 실측으로 99건 중 60건이 점검기 자신의 오탐이었다.

## 특허법에서 달라질 만한 곳

아래 셋은 코드로 확인해 **`config-patent.yaml` 에 반영해 두었다.**
나머지 둘은 실물을 봐야 하고, 진단(`convert diagnose`)이 대부분 알려준다.

- **사건번호 — 손댈 것 없다(확인).** 일련번호 자리에 제한이 없어(`\d+`)
  `2019후10500`(5자리)도 그대로 잡힌다. `후`·`허` 는 원래 등록돼 있었다.
- **심결·심판번호 — 넣어 두었다(확인).** `당`(당사자계) `원`(결정계)
  `취` `정` 과 그 재심(`재당` `재원` `재취` `재정`)을 `config-patent.yaml`
  에 더했다. 길이순으로 정렬되므로 적는 순서는 상관없다.
  ※ `원` 은 금액과 생김새가 겹친다. 콤마가 있으면 정규식이 막지만
  `12원34` 꼴은 사건번호로 잡힌다. 첫 변환 뒤 `caselist-*.txt` 에서
  `\d{2,4}원\d+` 을 한 번 훑어볼 것.
- **조문 인용 — `제N조의N` 은 받는다(확인). 법령명은 새로 붙였다.**
  민소법은 한 법뿐이라 `제265조` 로 충분했는데, 특허법 교재는 특허법·
  실용신안법·디자인보호법이 한 쪽에 섞여 `제29조` 만으로는 어느 법인지
  정해지지 않는다. `preserve.article.law_names` 에 적은 이름이 조문
  **바로 앞에 붙어 있을 때만** 프론트매터 `articles:` 에 함께 실린다
  (`특허법 제29조 제1항`, `구 특허법 제42조 제4항`). 앞 문단의 법령명을
  이어 붙이지는 않는다 — 원문에 없는 것을 지어내지 않기 위해서다(§4.8).
  목록이 비면 지금까지대로 조문만 싣는다.
나머지 둘은 확인됐고, 둘 다 손이 더 간다는 뜻이다.

- **사례집이 있다.** [3] 매핑 단계를 그대로 쓴다. 다만 사례집 문제 번호
  모양(`profiles.casebook.problem`)이 민소법의 `E-2.` 꼴일 근거가 없다.
  **안 맞으면 문제가 하나도 안 잡힌다.** 사례집에서 제일 먼저 볼 자리다.
- **출판사가 다르다.** 논점 윤곽 띠가 **있는 교재인지부터** 확인해야 한다.
  띠가 없으면 뭉개진 절 제목을 되찾을 근거가 통째로 사라지고, 절 점검
  (`audit-sections`)도 다른 방식으로 해야 한다.

### 다른 출판사라서 꺼 둔 것 — 글자를 바꾸는 규칙들

민소법 설정에는 그 교재의 OCR 을 실측해 만든 규칙이 섞여 있다. 근거가 그
교재에만 있으므로 옮겨 쓰면 **없는 것을 지어낸다.** `config-patent.yaml`
에서 「중립화」로 표시하고 꺼 두었다.

| 꺼 둔 것 | 켜 두면 무슨 일이 나나 |
|---|---|
| `legend.bonus.misread` / `misread_ascii` | 오인식 글자 하나가 줄 맨 앞에 오면 그 줄부터 **뒤 24줄까지** 인용 박스로 삼켜진다. 목록에 `느` 가 있어서 '느슨한…' 으로 시작하는 본문 한 줄이면 그 일이 난다 |
| `profiles.textbook.headings` 의 세 자리 논점번호 | 세 자리 숫자로 시작하는 아무 줄이나 논점 제목이 된다 |
| `profiles.textbook.split_prefer` | 위와 짝이다. 함께 되살린다 |
| `profiles.textbook.roman_heads_extra: {II: [H]}` | 'H' 로 시작하는 줄이 로마자 절 제목으로 둔갑한다 |

되살리는 순서는 늘 같다 — **실물에 그 요소가 있는지 보고 → 세고 → 켠다.**

## 새 세션 첫 명령

```bat
cd C:\MyCode\pdf2md\book2md
git pull

convert --config config-patent.yaml diagnose "특허법 PDF 폴더" --out 특허출력
```

진단 리포트(`특허출력\_reports\diagnosis-*.md`)를 보고 시작한다. 텍스트 레이어
유무, 단 수, 색 종류, 옆번호·두문자·별표 표본 수가 거기 다 있다.

### 진단을 보고 채울 다섯 자리

`config-patent.yaml` 안에 `TODO(진단)` 으로 표시해 두었다. **채우기 전에
전 범위를 돌리지 않는다.** 민소법 값이 그대로 남아 있는 자리들이다.

| 자리 | 무엇을 보고 채우나 |
|---|---|
| `running.never_heading` | 진단의 머리말·꼬리말 표본. **책 제목**을 적는다 |
| `legend.outline` | 논점 첫 줄에 띠가 있는지. 없으면 이 파이프라인의 절 복구가 통째로 다르게 간다 |
| `legend.sidenote.pattern` | `probe --lines` 로 우측 여백 번호 모양 |
| `legend.bonus` | 보너스 박스가 있는지. 있으면 표지가 어떻게 흘러나오는지 세어 목록을 새로 만든다 |
| `legend.exam_year` / `case_label` | 기출연도·판례 라벨 표기 |
| `profiles.textbook.headings` | 절 번호 모양. 논점에 번호가 붙는지 |
| `profiles.textbook.split_prefer` | 장 나누기 경계 |
| `profiles.casebook.problem` | **사례집 문제 번호 모양. 안 맞으면 문제가 하나도 안 잡힌다** |

그다음은 민소법 때와 같은 순서다 — **하나 먼저 → 검증 → 규칙 보완 → 전체.**

```bat
REM 줄마다 무엇으로 읽혔는지 — 띠·옆번호·번호 모양을 여기서 본다
convert --config config-patent.yaml probe "특허법 기본서.pdf" --lines --pages 40-60
convert --config config-patent.yaml probe "특허법 사례집.pdf" --lines --pages 20-40

REM 한 장만 시험 변환
convert --config config-patent.yaml run "특허법 기본서.pdf" --pages 120-145 --profile textbook --out 특허출력\기본서
REM 절 제목 전수 점검 — 맨 윗줄 「목차 띠를 읽은 파일 N/M개」를 가장 먼저 본다
convert --config config-patent.yaml audit-sections 특허출력 --out audit.md
```

사례집은 상·하로 나뉘어 있으면 **출력 폴더를 나눈다.** 같은 폴더에 쏟으면
문제 그룹 파일 이름이 겹친다 (README 참조).
